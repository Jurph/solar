# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

### Running the Server
```bash
# Windows
launch-django.bat

# Linux/macOS
./launch-django.sh

# Manual (from repo root)
cd mysite && python manage.py runserver
```

### Running Tests
```bash
# Run all fast tests (used in CI)
pytest tests -m "not slow"

# Run a single test file
pytest tests/test_route_planning.py

# Run a single test function
pytest tests/test_route_planning.py::test_function_name

# Run slow (LLM) tests
pytest -m "slow"

# Run with coverage
pytest tests -m "not slow" --cov=mysite/universe --cov-report=term
```

### Database & Migrations
```bash
cd mysite
python manage.py makemigrations universe
python manage.py migrate
python manage.py import_universe   # Load XML universe definition
python manage.py export_universe   # Export to XML
python manage.py start_simulation_loop   # Start the simulation clock
python manage.py audio_worker      # Start background TTS pre-generation
```

## Architecture

### Project Layout
The Django project root is `mysite/` (not the repo root). Tests live in `tests/` at the repo root, with `pytest.ini` and `DJANGO_SETTINGS_MODULE=mysite.settings` configured there.

The core application is `mysite/universe/` with three main layers:

**Models** (`universe/models/`) — Pure data definitions. Code should not call models directly from views; go through services instead.

**Services** (`universe/services/`) — All business logic. Primary façade services use `_server` suffix and expose a single public class (e.g., `route_server.py` → `RouteService`, `script_server.py` → `ScriptService`). Smaller helpers use `_service.py` naming or live in sub-packages.

**Views** (`universe/views/`) — Decomposed by domain concern. `views/__init__.py` re-exports all view callables for backward-compatible URL routing.

### Data Flow for a Mission
1. `spawn_mission` (views/missions.py) creates a `Ship`, calls `RouteService` to plan a route, calls `ScriptService` to convert `NavigationEvent`s into `DialogueEvent` chains, schedules them in `DialogueEventLog`.
2. `start_simulation_loop` advances simulation time via `SimulationState` singleton.
3. `audio_worker` (management command) pre-generates TTS audio ~1 hour ahead of playback; the web server never generates audio on-demand.
4. Frontend polls `event_feed` API, which time-gates events via `SimulationState`; checks `audio_ready` flag before playing.

### Inheritance Hierarchy
```
Location (concrete)
  └── Celestial (abstract)
      └── PhysicalBody (abstract)
          ├── Star
          ├── Planet
          └── Moon
```
`Atmosphere` is a separate model linked to Planet/Moon via Django `ContentType` (generic FK).

### Stored vs Calculated Properties
Source data (mass_kg, radius_km, orbital parameters) is stored in the DB. Derived values (surface gravity, escape velocity, unit conversions) are calculated via helper methods on `PhysicalBody` — do not add computed fields to the DB. See `docs/STORED_VS_CALCULATED_PROPERTIES.md` for the full decision table.

### Key Design Constraints
- **No on-demand TTS**: Audio is pre-generated by `audio_worker`; web views only serve existing files (returning 202 if pending).
- **Absolute imports**: Use `from mysite.universe.models.ship import Ship` style. Use local (inside-function) imports only to break circular dependencies.
- **Migrations**: Batch related schema changes before running `makemigrations` to minimize migration count. Squash periodically; never edit migrations that have run in production.

## Coding Standards

- Linter/formatter: **ruff** (incorporates black + flake8). Follow Black formatting and PEP 8.
- All functions require **type hints** and **docstrings**.
- Prefer absolute imports. Use local imports only to break circular dependencies.
- Tests mirror implementation files; use pytest style with descriptive docstrings. No trivial or degenerate tests. Do not test third-party library behavior.

## Critical Rule: Never Guess at Method Signatures

Before calling any class or function you haven't recently read, search for its definition and verify the exact signature. Guessing in a codebase this large reliably introduces bugs. If you cannot determine how to call something with high confidence, stop and ask.

When writing a block of code, afterward:
1. List every method/constructor called
2. Find each definition in the codebase
3. Verify the signature matches your usage
4. Fix mismatches before proceeding

## LLM Integration

`llm_service.py` connects to any OpenAI-compatible endpoint (defaults to Ollama at `localhost:11434`). The `slow` pytest marker gates all tests that make real LLM calls. LLM call timings are automatically logged to `artifacts/llm_benchmark.jsonl` by `conftest.py`.
